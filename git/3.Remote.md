# Working Remotely Workflow

See also: [Git basics](1.git.md) · [Branching](2.git%20branch.md)

A **remote** is a named URL of another copy of the repository (`origin` by default). `origin/main` is a **remote-tracking branch**: your local, read-only snapshot of `main` on `origin` the last time you fetched.

## Create and connect to your remote repository

In our local machine, inside our sources folder:

```bash
# Optional, create a readme:
echo "# foo" >> README.md

# init our local repository (on branch main)
git init -b main

# add the files to the staging area
git add .

# commit the files
git commit -m "First commit"

# Link the local and the remote repository (create the EMPTY repo on GitHub first):
git remote add origin https://github.com/artur/foo.git
# or with SSH: git remote add origin git@github.com:artur/foo.git

# we can verify with
git remote -v
```

```text
origin  https://github.com/artur/foo.git (fetch)
origin  https://github.com/artur/foo.git (push)
```

## Upload your changes to the remote repository

The first time, set the **upstream** (the remote branch your local branch tracks):

```bash
git push -u origin main
```

From this point, every time we want to push changes to the server:

```bash
git push
```

With `git config --global push.autoSetupRemote true`, a plain `git push` on a new branch creates the remote branch and sets the upstream automatically.

```bash
git branch -vv                  # see which upstream each branch tracks
git branch -u origin/main       # set the upstream of the current branch by hand
git status -sb                  # ## main...origin/main [ahead 2, behind 1]
```

## Retrieve last updated version from GitHub

We have two options:

### Option 1: fetch + merge (or rebase)

```bash
# download changes into .git (updates origin/*), your files are not touched:
git fetch origin

# see what came in before integrating it
git log --oneline main..origin/main

# merge the changes into my branch:
git merge origin/main
# or put my local commits on top of them:
git rebase origin/main
```

### Option 2: pull

```bash
# fetch and merge at the same time:
git pull                 # uses the upstream of the current branch
git pull origin main     # explicit
git pull --rebase        # fetch + rebase instead of merge
git pull --ff-only       # only if it can fast-forward, otherwise fail
```

`git pull` = `git fetch` + `git merge` (or `git rebase` with `pull.rebase true`). Conflicts are the same in both options; the difference is that with `fetch` you can review the changes before integrating them.

```bash
git config --global pull.rebase true   # avoid the "how to reconcile divergent branches" warning
```

## Fetch options and pruning

```bash
git fetch --all          # all remotes
git fetch --prune        # also delete origin/* refs whose branch was deleted on the server
git config --global fetch.prune true   # prune on every fetch
git remote prune origin  # prune only
```

## Remote branches

```bash
git branch -r                          # list remote-tracking branches
git ls-remote --heads origin           # ask the server directly
git switch feature-x                   # create local branch tracking origin/feature-x
git push origin --delete feature-x     # delete a branch on the remote
git push origin :feature-x             # same, old syntax
git push origin local:remote-name      # push a local branch with another name
```

## Rewriting pushed history: force push

After `git commit --amend` or `git rebase` on a branch that is already pushed, a normal push is rejected. Use:

```bash
git push --force-with-lease
```

It only overwrites the remote if it is still where you last saw it, so you don't delete a teammate's commits. Plain `--force` overwrites blindly. Never force push to a shared `main`.

## Forks: keep your copy up to date

```bash
git clone git@github.com:artur/project.git            # your fork
cd project
git remote add upstream https://github.com/original/project.git
git remote -v
```

```text
origin    git@github.com:artur/project.git (fetch)
origin    git@github.com:artur/project.git (push)
upstream  https://github.com/original/project.git (fetch)
upstream  https://github.com/original/project.git (push)
```

```bash
# sync your main with the original project
git fetch upstream
git switch main
git merge --ff-only upstream/main      # or: git rebase upstream/main
git push origin main

# work on a branch and open a Pull Request from your fork
git switch -c fix/typo
git push -u origin fix/typo
```

## How to change remote repository

To work with a different repository, change the URL of the remote:

```bash
git remote set-url origin https://gitlab.com/bar.git
```

Or remove the old and add the new one:

```bash
# remove old
git remote remove origin

# add new
git remote add origin https://gitlab.com/bar.git
```

```bash
git remote rename origin old-origin   # rename a remote
git remote show origin                # details: URL, branches, tracking
```

## Rejected push

If you get the error message:

```text
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/artur/foo.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
```

Someone pushed before you. Integrate their work and push again:

```bash
git pull --rebase
git push
```

If the remote was created with its own README/license (two repos without common history), the pull fails with `refusing to merge unrelated histories`. Only in that case:

```bash
git pull origin main --allow-unrelated-histories
```

## SSH instead of HTTPS

```bash
ssh-keygen -t ed25519 -C "artur@example.com"   # creates ~/.ssh/id_ed25519(.pub)
cat ~/.ssh/id_ed25519.pub                      # paste it in GitHub > Settings > SSH keys
ssh -T git@github.com                          # "Hi artur! You've successfully authenticated..."
git remote set-url origin git@github.com:artur/foo.git
```

The same key can sign commits, see [Git basics](1.git.md#signing-commits-with-ssh).
